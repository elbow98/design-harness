# critique — 기준표로 보는 디자인 리뷰

사용자는 디자인 용어를 모른다. 그래서 리뷰는 **현상 → 왜 문제인지(사람이 어떻게 느끼는지) → 고칠 곳 → 고친 뒤 기대 효과** 순서로 쓰고, 용어는 처음 한 번 풀어 쓴다.
판정 기준은 Design.md다. 내 취향이 Design.md와 다르면 Design.md를 따른다.

근거: Anthropic 하네스 설계 글(생성기·평가기 분리, few-shot 보정), impeccable `critique`(Nielsen 채점·P0~P3·앵커링 금지), taste-skill(단일 목적 패스·점수 캡·수정 순서·3라운드), UICrit(UIST 2024)·Duan(CHI 2024)(위치 표시가 품질을 올리고, LLM은 없는 위반을 지어낸다). 정리: `vault/taste/README.md` 하단 참고 링크.

## 0. 준비 — 기계 검사와 분리
1. `scripts/verify.sh <대상>`을 돌린다. check(토큰 드리프트)·slop(AI 티)·shot(4장 + 넘침·콘솔 + 접근성) 중 **실패가 있으면 그것부터 고친다.** critique는 기계 검사를 통과한 화면에 판단을 얹는 단계다.
2. 마지막 줄의 스크린샷 폴더를 받는다.
3. **리뷰는 화면을 만든 맥락과 분리한다.** Agent 도구로 새 서브에이전트를 띄워 이 SKILL.md, `Design.md`, 스크린샷 4장 경로, 화면의 목적 한 줄만 준다. 코드·대화 맥락·slop/a11y 결과는 주지 않는다. 분리할 수 없으면 보고 첫 줄에 `⚠ 단일 맥락 리뷰`를 적는다.
4. 보정 예시: `vault/taste/`에 같은 `kind`이면서 `score:`가 붙은 사례가 있으면 1~2개를 먼저 읽고 기준을 맞춘다.

## 1. 단일 목적 패스 (한 번에 한 관점, 각 한 줄)
4장을 모두 Read로 연다. 데스크톱 라이트를 기준으로 보고, 나머지 셋에서는 "그 뷰에서만 깨지는 것"을 찾는다.
1. **1초**: 가장 먼저 보이는 것 하나. 그게 이 화면의 목적(핵심 숫자·주 행동)인가?
2. **찡그려 보기**: 흐리게 보면 덩어리가 2~3개로 줄어드는가? 가장 큰 덩어리가 목적이 아니면 항목 1은 0점.
3. **이름 가리기**: 서비스 이름을 지워도 이 사업·이 데이터를 위한 화면으로 읽히는가, 아무 SaaS 템플릿처럼 보이는가?
4. **가장자리**: 왼쪽 가장자리 x 위치 개수(2~3개가 좋다).
5. **간격**: 섹션 사이 간격이 섹션 안 간격보다 확실히 큰가? 빈 곳이 쉼인가 구멍인가?
6. **글자**: 크기 종류 5개 이하인가, 제목 끝에 홀로 남은 단어, 75자 넘는 줄.
7. **색**: 색마다 역할 이름을 붙일 수 있는가(항목 7).
8. **상태**: 빈·로딩·에러·경고 중 하나라도 보이는가.

## 2. 기준표 (0~2점: 0 문제 있음 / 1 애매 / 2 좋음)

| # | 항목 | 무엇을 보나 | 흔한 실패 |
|---|---|---|---|
| 1 | **시선 순서** | 3초 동안 눈이 가는 순서 1→2→3. 1번이 이 화면의 목적인가 | 장식·로고·필터가 1번. 모든 게 같은 굵기라 순서가 없음 |
| 2 | **한 화면 한 주인공** | 가장 큰 글자, 유일한 primary 버튼, accent가 같은 이야기를 하는가. accent 3곳 이하 | primary 2개, accent가 아이콘·배지·링크에 흩어짐 |
| 3 | **정렬선** | 왼쪽 가장자리 정렬선 개수. 적을수록 좋다 | 패널마다 안쪽 여백이 달라 글자 시작점이 들쭉날쭉 |
| 4 | **간격 그룹** | 관련된 것은 `--sp-2~3`로 붙고, 다른 그룹은 `--sp-8` 이상 떨어지는가(Design.md §4). 간격만 보고 무리를 나눌 수 있어야 한다 | 모든 간격이 16px 근처로 같아 묶음이 안 보임 → 선·박스를 더 그어 해결하려 함 |
| 5 | **밀도** | 도구 화면이면 조밀 타입 단계(`--fs-d-*`)를 썼는가. 빈 공간이 의미 있는가 | 대시보드에 글 중심 행간(1.65), 카드 하나에 숫자 하나 |
| 6 | **위계 수단** | 위계를 크기·굵기·간격으로 먼저 만들었는가. 박스·선·그림자·색은 그다음 | 카드+그림자로 모든 걸 감쌈, 패널 안 패널 |
| 7 | **색 역할** | 강조 / 시장 방향(up·down) / 좋고 나쁨(positive·negative) / 범주 / 순차 중 무엇인가. 이름을 못 붙이면 뺀다 | 증감률에 초록/빨강(시장 데이터는 빨강/파랑), 항상 같은 색인 지표 |
| 8 | **숫자 읽기** | Design.md §10: 단위·자릿수·부호·tabular-nums·숫자 열 우측/날짜 열 좌측 | `12345678원`, `+-`, %와 %p 혼동, 열마다 소수 자릿수 다름 |
| 9 | **문구** | Design.md §11: 해요체, 능동형, 버튼은 일어날 일, 에러는 무엇이+다음 행동, 용어집과 일치 | `확인`·`취소` 남발, `오류가 발생했습니다`, `데이터 조회 실패` |
| 10 | **한글 조판** | 단어 중간 줄바꿈 없음(`keep-all`), 한 줄 68ch 이하, 버튼·배지 라벨이 두 줄로 안 깨짐 | 390px에서 "포트폴 / 리오" |
| 11 | **상태** | 빈·로딩·에러·긴 이름·hover·focus를 볼 수 있는가(Design.md §7). 목업에 상태가 하나는 있는가(§6 대시보드 화면) | 데이터가 딱 맞는 이상적인 상태만 존재 |
| 12 | **모바일·다크** | 390px에서도 주인공이 첫 화면에 보이는가. 다크에서 테두리·격자가 사라지지 않는가 | 모바일 첫 화면이 필터로 가득, 다크에서 표 구분선 실종 |

**점수 캡** — 아래 중 하나라도 있으면 총점과 무관하게 판정은 `수정 필요`:
0점 항목 존재 · slop.sh 실패 잔존 · 숫자 열 좌측 정렬 · 제목·값을 가리는 요소 · 390px 가로 스크롤 · 자리표시 문구(Lorem, "텍스트", "제목").

**자기 채점 경계** — 단일 맥락 리뷰에서 거의 만점(22점 이상)이 나오면 "이 화면을 처음 보는 리뷰어"로 다시 채점하고 두 점수를 다 적는다.

## 3. 대시보드 휴리스틱 (도구 화면일 때, 0~4점)
Nielsen 10개 중 대시보드에서 가장 자주 무너지는 넷. 해당 없으면 `n/a`로 두고 만점을 다시 계산한다.
- **#1 상태 가시성**: 데이터 기준시점, 로딩, 갱신 실패가 화면에 보이는가
- **#4 일관성**: 같은 종류의 숫자는 같은 형식, 같은 행동은 같은 동사인가
- **#6 기억보다 인식**: 적용된 필터·기간이 화면에 보이는가(드롭다운을 열어야 아는가)
- **#8 최소주의**: 0점 = 모든 요소가 같은 강도로 주의를 다툼 / 4점 = 모든 요소가 자리 값을 함

## 3-1. 슬라이드일 때 (Design.md §13)
스크린샷 4장 대신 **각 장을 1920×1080으로 렌더한 이미지**를 받는다(Slides Artifact는 각 장 스크린샷, HTML 덱은 `scripts/shot.sh` 대신 Playwright로 장마다 1920×1080). 단일 목적 패스를 이렇게 바꾼다.
1. **제목만 읽기**: 모든 장의 제목을 이어 읽으면 이야기가 되는가. 명사형 제목(`3분기 실적`)은 항목 1을 0점.
2. **25% 축소**: 480×270으로 줄여도 제목과 주인공 숫자가 읽히는가(뒷자리 관객).
3. **한 장 한 메시지**: 장마다 주장을 한 문장으로 적을 수 있는가. 두 문장이 나오면 나눌 장.
4. **분량**: 불릿 3개·각 2줄, 표 5×5, 차트 하나를 넘는 장 목록.
5. **강조색**: 장마다 강조색이 한 곳인가, 차트에서 강조 계열 하나만 색인가.
6. **출처**: 숫자가 있는 장에 출처·기준시점이 있는가.
기준표 12항목 중 5(밀도)·11(상태)·12(모바일)는 `n/a`, 8·9·10은 그대로 본다. 보고의 위치는 `장 번호 + 영역`(`7장 오른쪽 차트`).

## 4. 지적 쓰는 규칙 (환각 방지)
- **위치 없는 지적은 쓰지 않는다.** 어느 스크린샷(`desktop-light`), 어느 영역(좌상단 KPI 줄 2번째 칸), 가능하면 셀렉터.
- 다 쓴 뒤 **같은 스크린샷을 다시 열어** 그 현상이 실제로 보이는지 확인하고, 안 보이면 지운다.
- px·대비비 같은 숫자는 눈대중으로 쓰지 않는다. Playwright로 computed style을 재거나 `a11y.json`에서 가져온다.
- **심각도**: P0 사용 불가(값이 잘림·버튼 안 눌림) / P1 사용자가 이것 때문에 문의하거나 잘못 읽는다 / P2 어색하지만 쓸 수 있다 / P3 다듬기. P3는 3개까지만.
- 확실하지 않은 지적은 `(취향 문제)`로 표시한다.
- **기계 검사와 대조는 판단을 다 쓴 뒤에.** 그때 `slop`·`a11y` 결과를 열어 "기계만 잡은 것 / 리뷰만 잡은 것 / 오탐"으로 나눈다. 먼저 보면 판단이 거기 끌려간다.

## 6. 고치기 (사용자가 "고쳐줘"라고 하면)
- **순서**: 위계 → 구성(정렬·간격) → 글자 → 색 → 상태·디테일 → 움직임. 앞 단계 문제가 남아 있으면 뒤 단계는 손대지 않는다.
- 하나씩 적용하고 `scripts/diff.sh compare` 또는 shot 재촬영으로 전후를 본다.
- 프로토타입이면 Rules.md §5-7대로 `-v2` 폴더에서. 기존 앱이면 그 프로젝트 규칙대로.
- **재검은 새 리뷰어로.** 라운드마다 새 서브에이전트에게 새 스크린샷만 준다(같은 리뷰어를 되풀이하면 유용성이 떨어진다). **최대 3라운드.** 그래도 0점이 남으면 남은 문제를 그대로 보고하고 멈춘다.
- 사용자가 지적을 거절하면 그것도 교정이다. Rules.md 교정 로그에 적는다(wrap-session에서 승격 판단). 좋은 판정이 난 화면은 `score:`를 붙여 `vault/taste/`에 보정 예시로 넣자고 제안한다.
